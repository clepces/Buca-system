📌 SECCIÓN DE MODIFICACIONES, NOTAS Y OPINIONES DE ARQUITECTURA - ANTIGRAVITY (2026-05-25)

1. 🛠️ MODIFICACIONES REALIZADAS (RESOLUCIÓN DE INCONSISTENCIAS / CABLES CORTADOS):
   - [COMPLETADO] EventBus: Se implementó de manera nativa y robusta el método 'once(event, callback)' en
     'src/core/eventBus/index.js' para soportar suscripciones de un único uso. Esto resolvió el crash
     fatal de cambio de layout que se producía en 'router.js:L136' ("TypeError: eventBus.once is not a function").
   - [COMPLETADO] EventBus - Sincronización Segura: Se optimizó el método 'emit()' para clonar el array
     de callbacks antes de iterar, evitando condiciones de carrera si un evento se desuscribe durante la emisión.
   - [COMPLETADO] GraphicsEngine - Fugas de Memoria y CPU: Se re-escribió 'destroy()' en 'src/core/engine/graphics.js'
     para detener de forma limpia todos los procesos de fondo y sensores que quedaban huérfanos:
     - Detención del timer periódico '_stateSyncInterval'.
     - Desconexión del 'mutationObserver' y del 'intersectionObserver' (libera VRAM y nodos del DOM).
     - Detención de 'memoryGuard', 'reflowGuard' y 'ghostSanitizer' al apagar el motor.
     - Detención formal de 'thermalMonitor' usando su método '.stop()' (antes se buscaba el inexistente '.disconnect()').
     - Reset de la instancia estática ('GraphicsEngine.#instance = null') para admitir inicializaciones limpias de cero.
   - [COMPLETADO] ResourceThrottle: Se creó el método 'stop()' en 'src/core/engine/services/ResourceThrottle.js'
     para desregistrar los event listeners de window ('graphics:tier-changed' y 'buca:perf_critical_network_pause')
     durante la parada del motor, evitando fugas pasivas en el Garbage Collector.

2. 🧠 CRÍTICA Y DIAGNÓSTICO DE LA ESTRUCTURA MODULAR ACTUAL DE BUCA:
   - Estado Actual: La separación en "Core", "Modules" y "Shared" es EXCEPCIONAL. Refleja un diseño de software
     maduro, escalable y muy robusto para una SPA pura sin frameworks (Vanilla JS + Vite).
   - El Motor Neural (BNE): Un acierto absoluto. Integrar telemetría en tiempo real y perfiles (eco, balanced, ultra)
     garantiza accesibilidad y rendimiento premium en hardware heredado (Eco L0) y de última generación.
   - El Flujo de Autenticación: Diseñado con transiciones fluidas de "Corporate Hybrid Glass" que aumentan el valor
     percibido del software, manteniendo la modularidad al 100% (evitando que auth o el panel se mezclen).

3. 🚀 IDEAS NUEVAS Y RECOMENDACIONES DE ARQUITECTURA A FUTURO:
   - IDEA 1: Router Dinámico Desacoplado:
     Actualmente, los módulos registran sus rutas cargando dinámicamente sus carpetas. Recomiendo que el Router Core
     implemente una política "strict modules" donde cada módulo exporte un manifiesto JSON con sus rutas de acceso.
     Esto permitirá que la aplicación deshabilite módulos completos en caliente (ej. si el usuario no tiene la suscripción
     activa) sin tener que tocar una sola línea de código del Core.
   - IDEA 2: Implementación de un "State Time-Travel / Snapshots":
     Dado que todo el estado se gestiona centralizado en 'src/shared/state/', podríamos implementar un helper en el
     State Store que guarde instantáneas (snapshots) del estado actual del panel. Si el cliente tiene mala conexión,
     podrá restaurar el estado exacto del panel de transacciones al instante en que se desconectó.
   - IDEA 3: PWA & Service Worker Avanzado:
     Optimizar 'sw.js' para cachear agresivamente las colecciones de Firestore estáticas del negocio (como la lista de productos)
     usando IndexedDB. De esta manera, el sistema podrá trabajar de forma 100% OFF-LINE completa en zonas con conexión
     inestable (típicas en negocios de Venezuela), sincronizando transacciones en segundo plano una vez que la red retorne.
   - IDEA 4: Sistema de Permisos Basado en Claims:
     Mover la validación de 'permissions.js' a un modelo basado en JSON Claims dentro de 'users/${uid}' en Firestore.
     Esto evitará hardcodear roles a nivel de frontend y permitirá que las reglas de Firebase ('firestore.rules')
     bloqueen peticiones en tiempo real de forma dinámica.

│       │  COMENTAR AQUI:
│       │  [Antigravity]: "ui-bridge.js" es sumamente útil, pero tiene un propósito muy específico:
│       │  Sirve como un "puente" que expone funciones (como window.toggleTheme o window.openModal) directamente al objeto global "window".
│       │  Esto es necesario porque la aplicación renderiza interfaces mediante plantillas de texto HTML, y los manejadores inline como "onclick='toggleTheme()'" no pueden ver el código empaquetado por Vite a menos que esté en "window".
│       │  ¿Es perjudicial? No lo es, siempre y cuando solo se use para controles globales básicos (tema, apertura de modales de asistencia, scroll del dock). Para lógica interactiva avanzada de los módulos, es mucho más limpio y seguro programar escuchas de eventos internos de forma modular ("addEventListener") y removerlas al salir, evitando la sobrepoblación del objeto global "window".

│         NOTA: BUENO AQUI LOS MODULOS LOS MODULOS ES UNA DE LA AREA MAS IMPORTANTES COMO SABEMOS 
│         LOS MODULOS NO SON SOLO HERRAMIENTAS SON MODULOS UNIVERSALES EN LA QUE TIENE SU PROPOCITO
│         FUNCIONAL Y VISUAL PERO TAMBIEN TIENE COMO LA FINALIDAD DE INTERACTUAR CON OTRO MODULOS BASADO 
│         EN LOS PERMISO DEL NUCLEO YA QUE NO PODEMSO PERMITIR QUE ENTRE MODULOS PASE ALGO SI SABE QUE ES YA 
│         TENEMOS COMO FINALIDAD PROTEGER LOS DATOS Y TODO LO QUE INTERATUA ENTRE SI.           
│         
│         LO BUENO DE LOS MODULOS ES QUE PERMITE EMPORTA Y IMPORTA HERRAMIENTAS ENTRE SI Y ESTO 
│         EVITA REPETIR CODIGO EL MODULO AUTH ES UNO DE LOS MAS UTILIZADO YA QUE SU PROPOCITO ES AUTENTIFICAR 
│         Y ESO ES LO MAS IMPORTANTE EN LA PARTE DE VALIDA CIERTAS ACCIONES POR SUPUESTO NOSOTRO SI DESARROLAMO
│         UN MODULO TEMEMS QUE TENER EN CUENTA VARIAS COSA UNA ES SI UN CODIGO QUE ESTAMOS CREADO ES REUTILIABLE         
│         ESTE NO SE INCORPORARIA DE FORMA MODULAR YA QUE OTRO MODULOS LO UTILIZARIA POR LO TANTO SE PODRIA EN FORMA         
│         GLOBAL PARA QUE CUALQUIER MODULO LO UTILICE ESTO SI NECESITAMOS TENER CUIDADO NO SOLO EN EL MODULO A DESARROLLA          
│         SI NO QUE AL NIVEL INTERNO.          
│                  
│         ESTO APLICA PARA CUALQUIER AREA SEA CSS (SASS), SERVICES, LOGICS, COMPONENTS  Y MAS       
│         POR LO TANTO HAY QUE SIEMPRE VERIFICAR ESTO PARA EVITAR DUPLICAR COSA Y GENERA MAS PROBLEMA A LA APLICAICON         
│         COMENTAR AQUI:
│         [Antigravity]: Exacto. Los módulos (como auth y workspace) deben estar 100% aislados. Ningún módulo debe importar
│         un componente de otro módulo directamente. Toda la comunicación entre ellos debe ocurrir a través del EventBus o
│         actualizando estados compartidos en el State Store (store.js). Esto evita que se "corten los cables" si eliminas un módulo.
